# Rideforge

A React Native Android prototype for Yash's Platina 110. Built from scratch with Expo native development builds, TypeScript, SQLite, phone GPS, and ESP32 BLE. This is a native mobile application, not a website. Expo Go is not supported for BLE/background tracking.

## Run on your Android phone

Requirements: Node 20.19.4 or newer, JDK 17, Android Studio and SDK, USB debugging enabled, and an authorized device visible in `adb devices`.

```sh
npm ci
npx expo run:android --device
```

After the initial build, start Metro with `npm start`. Rebuild after native dependencies/configuration change. The app's `android` project is generated by Expo; native code is not included in this source archive. A release APK can be built after prebuild using Gradle and an appropriate release signing configuration. Do not ship debug signing as a production release.

On the Narzo 70 Turbo, grant Bluetooth, notifications, and location permissions. Recording with the screen locked requires background location permission. Test actual device battery restrictions before relying on recording. Permissions alone do not prove background reliability.

## Implemented in this increment

- Minimal light interface: warm-white background, charcoal text, muted green actions, serif typography.
- Subtle 110 ms button fades and 160 ms section fades; respect reduced-motion setting.
- Cockpit, ride history, fuel/refill records, map/navigation, device setup.
- SQLite persistence, continuous GPS sample writes, paused/finished ride states, app-restart recovery.
- Start a ride directly from Cockpit, with optional destination setup and bike sensor connection. Automatic start on movement remains optional.
- Active ride banner across all tabs; navigation stays mounted and saves its route, destination, guidance progress, and voice preference in SQLite.
- Heading-up map follow uses GPS travel direction when moving and phone compass at low speed. Zoom adapts to speed and proximity to the next turn; drag to browse and recenter to resume.
- Cockpit shows saved refill totals, recorded spend, latest refill, and full-to-full mileage.
- Explicit pause/resume/end controls; pause stops the recording location service and retains the same ride. End confirms and saves it; starting/resuming does not duplicate the ride.
- On reopening/foregrounding the app, recovery checks for a stopped location task and attempts to restart tracking for an active or armed ride. OS force-stop gaps cannot be recovered.
- BLE scan/connect, notification, newline-delimited telemetry decoding, stale-reading indication.
- ESP32-S3 potentiometer firmware with service-filtered advertising, notification subscription handling, 20-byte BLE chunks, smoothing, Serial diagnostics, and advertising restart after disconnect.
- Real manual full-to-full fuel economy, including partial fills and weighted overall mileage.
- Simulated dashboard preview that does not insert fake rides/refills.
- Leaflet map inside a native WebView, Photon destination search, OSRM route preview, foreground voice/turn guidance, conservative reroute detection.

## Times New Roman

Times New Roman is not installed on stock Android and is not redistributed in this archive. Until you supply the licensed font, Android uses its system serif. To enable the requested font:

1. Put your licensed regular font at `assets/fonts/times.ttf`.
2. Run `node scripts/configure-font.mjs`.
3. Restart Metro/rebuild the app.

See `assets/fonts/README.md`. The UI loads it as `TimesNewRoman`; synthetic bold may be used by Android. Actual licensed bold/italic variants can be added later. Do not claim the fallback is Times New Roman.

## First bench test

1. Power the ESP32 by USB.
2. Connect a potentiometer's outer terminals to 3V3 and GND; wiper to GPIO1.
3. Open `firmware/Rideforge/Rideforge.ino` in Arduino IDE using the ESP32 Arduino core and the matching S3 board configuration.
4. Upload, open Device in the app, and tap Connect ESP32 & arm recording.
5. Turn the potentiometer. Readings must remain labelled simulated.
6. Test phone recording outdoors by walking/riding safely; sustained speed threshold is 2 m/s for 4 seconds. Slow walking may not start it. No screen interaction while riding.
7. Pause, restart the app, resume, and finalize; verify history persists.

This is a bench wiring guide only. The bike converter has not been purchased. Do not connect a bike's 12 V line or fuel sender to the ESP32 GPIO. Vehicle power/input conditioning and measured calibration are separate engineering work.

## Important limitations

- No compiled APK or physical-device test was performed here; this environment has no configured Android SDK/device.
- BLE connection begins explicitly from Device. Automatic reconnect after process termination, boot auto-start, and a background BLE service are not implemented.
- Foreground-service phone location is configured but must be validated on the user's Android 16 phone. Force-stop will stop tracking.
- BLE disconnection does not imply ignition-off. The sample firmware has no ignition input. A future validated `ignition:false` frame pauses the ride and prompts; repeated false frames are suppressed.
- No standalone GPS module, independent ESP32 distance recording, store-and-forward sync, or actual tank calibration yet.
- No measured per-ride fuel consumption. Per-ride fuel estimates reuse historical overall mileage. Simulated fuel is never used for real mileage calculations.
- Guidance continues across tabs while the app is in the foreground. Background/locked-screen voice navigation, production map matching, route alternatives, route replay, and motorcycle-specific routing are future increments. Saved recording is separate from foreground guidance.
- Navigation displays live remaining distance and a time estimate scaled from the original route duration; it is not a traffic-aware arrival prediction. Route progress uses segment projection, with simple crossing and GPS-jump safeguards. It still needs road testing.
- Map search/routing use public demo services without uptime guarantees. Default routing is a driving/car profile: verify motorcycle access. No live traffic. No offline tile downloading.
- Map tiles and Leaflet resources require internet. Map/search/route requests disclose location/destination to third-party services. No cloud account or ride-history backend is used.
- Recorded GPS points are stored; history currently exposes sample count, not replay.
- No data export or sync protocol yet. Individual rides/refills can be deleted from their history cards; Device includes a full local-data reset.

## BLE protocol v1

Service: `4fa869d1-1736-43c4-a393-b00e5a5a4309`

Notify characteristic: `4fa869d2-1736-43c4-a393-b00e5a5a4309`

ASCII JSON frames terminated by newline, fragmented into 20-byte chunks:

```json
{"v":1,"fuelPct":65.2,"simulated":true}
```

Optional future `ignition` boolean must come from a real validated signal. Firmware must not infer it from BLE connection state. Frames above 4096 buffered bytes are discarded. No command or history sync characteristic is implemented yet.

## Ride and navigation regression checks

1. In Cockpit, tap Set destination, select a route, then return to Cockpit and tap Start ride. The ride starts immediately; the selected route begins guidance. A destination and BLE sensor are optional.
2. Switch through Fuel, Rides, Cockpit, and Navigate. Confirm the same ride distance, destination, and route remain.
3. Drag the map to browse; tap Recenter & follow to restore automatic camera tracking. Verify heading outdoors, speed-based zoom, and close zoom near turns.
4. Pause and resume; confirm the same ride continues. End & save should finish that ride and clear the active navigation session.
5. Restart the app during an unfinished ride. Confirm ride/refill records and the navigation session restore; check GPS service recovery on the phone.
6. Log real full/partial refills and confirm Cockpit shows the latest refill, totals, and eligible full-to-full mileage after restart.

Map rotation uses the pinned [Leaflet Rotate 0.2.8 plugin](https://github.com/Raruto/leaflet-rotate), loaded alongside Leaflet in the WebView.

## Mounted riding screen

Starting or restoring an unfinished ride opens a dedicated portrait riding screen. The map occupies 70% of the available safe-area content; the remaining 30% shows a large GPS speedometer (km/h), fuel percentage/bar, trip distance, and Pause/Resume/End controls. The header and tabs are hidden in this mode. Use Cockpit to return to the normal screens without stopping the ride, and Open ride view to return.

The same navigation component stays mounted through these layout changes. Turn directions, destination, recenter, and voice controls overlay the map. A destination is optional: free rides still display the phone position. GPS speed updates are requested every second and readings older than five seconds or with poor/unknown accuracy are shown as unavailable. Fuel remains clearly labelled simulated or stale as appropriate.

Phone checks: start a ride, confirm the 70/30 layout fits the mounted phone, verify speed against a reliable reference, return to Cockpit and reopen ride view, then pause/resume/end. Test real compass and GPS behavior outdoors. Device screen timeout still follows Android settings.

## Delete records and start fresh

- Rides: Delete ride removes that entry and its stored GPS points after confirmation. Deleting an unfinished ride stops its recording first.
- Fuel: Delete fuel entry removes the refill after confirmation. Dashboard totals and eligible mileage intervals recalculate from the remaining records.
- Device → App data → Reset all app data: after confirmation, stops recording and navigation, disconnects BLE, clears notifications, and deletes all rides, GPS points, refills, saved navigation, and settings. The app returns to a fresh Cockpit with empty forms and default preview state. Android permissions are managed by the operating system and are retained.
- Deletions are permanent. Full reset and ride/point deletion use database transactions to prevent partial deletion on errors. Pending GPS and navigation writes are stopped/drained before reset.

## Tab bar and route progress

The five-tab bar now uses consistent Ionicons, a rounded white surface, and a filled green selected icon. The mounted ride view still hides the tab bar.

During guidance, the completed route is gray and the remaining route is green. The position marker is a directional arrow that rotates correctly in both following and map-browsing modes. GPS course is preferred when moving, with movement-bearing fallback when course is unavailable.

Off-route detection measures distance to road segments rather than sampled vertices. Two accurate off-route fixes trigger a route request (at least 60 m away, adjusted for GPS accuracy, or substantial backward travel). Requests are limited to one in flight with a 15-second cooldown and retry on later location updates if service requests fail. Previous completed sections remain gray after rerouting. Progress checkpoints restore with the saved navigation session.
